## 最初にやろうとしてたこと
- 着席認証（seat auth）で使った PM を会計（bill payment）でも再利用する

## 実際にやったこと
- 予約ごとに Stripe Customer を作成し PM を保持する仕組みを実装
- seat auth PI に setup_future_usage: on_session を追加
- stripe_customers テーブルを作成し customer_id をサーバーサイドで管理
- bill PI に customer を強制し、null なら fail fast する設計を追加
- seat auth と予約作成の reservation_id を揃えて整合させた
- 来店中（checkedin/ordered）の重複予約をブロックするガードを追加
- visitSession が欠けている場合の on-the-fly 生成を submitOrder に追加
- LP をユーザー/店舗タブ切り替え＋パステルテーマに全面リデザイン
- Basic Auth ミドルウェアでデモ保護を実装
- 本番ドメインを imasugu.jp に変更

## 横道に逸れたこと
- PM 再利用のために Customer 作成が必要と判明し、stripe_customers テーブルの設計が発生した
- setup_future_usage を後から追加したことで既存 PI の設計変更が連鎖した
- bill PI への customer 強制 → 既存フローに null が流れるケースを潰す修正が波及した

## なぜ逸れたか
- 「PM を再利用する」という要件は、Customer がないと Stripe 側で PM をアタッチできない制約を見落としていた
- setup_future_usage は PI 作成時に設定しないと効かないため、後からの追加が既存設計を壊した
- 予約作成と seat auth のどちらが先に走るか不定で、reservation_id がズレるタイミング問題が起きた

## 反省
- Stripe の Customer / PaymentMethod / PaymentIntent の関係を先に整理してから設計すべきだった
- setup_future_usage のような「PI 作成時にしか設定できない」制約は事前に確認する
- タイミング依存を許す設計は後で必ず問題になる。Customer テーブルで依存を切ったのは正しかった

## 学んだこと
- stripe_customers テーブルを挟むことで「予約と seat auth のどちらが先か」というタイミング依存を断ち切れる
- bill PI に customer を強制 + null で fail fast は「壊れている前提で防衛する」設計として有効
- setup_future_usage: on_session は PI 作成時に付けないと機能しない。後付け不可

## 備忘
- デモ保護 Basic Auth が本番環境に影響しないか確認する（Cache-Control の動作含む）
- visitSession の on-the-fly 生成は暫定対応。正規フローでの生成漏れを根本修正すべき
