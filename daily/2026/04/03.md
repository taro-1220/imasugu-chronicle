## 最初にやろうとしてたこと
- Supabase dual-write を全 Turso 書き込みに追加して本番カットオーバー準備を進める

## 実際にやったこと
- 全 Turso 書き込みに Supabase dual-write を追加（Phase 3）
- Supabase migration SQL を追加
- reconcile バッチ実装（未完了決済の自動回復、バックログ可視化・アラート付き）
- payment-store に webhook/reconcile/finalize 用ストアヘルパー 4 件を追加
- safeFetch ヘルパーを実装し response.ok 漏れを共通化
- API 呼び出し全体（submitOrder、handleRegister、waitForServerPaid、release-seat-auth、payment recovery）の response.ok チェック漏れを修正
- INVALID_TRANSITION のサイレント無視を廃止してエラーを明示するように変更
- チェックイン同期を await → fire-and-forget に変更
- mark_paid / order_submitted の fromStatuses に reserved を追加
- deprecated な update-status を /api/reservations/action に移行

## 横道に逸れたこと
- dual-write 追加を始めたら、response.ok チェックがほぼ全 API 呼び出しから抜けていることが発覚し、修正が波及した
- INVALID_TRANSITION のサイレント無視を廃止することになり、状態遷移の設計を見直す必要が生じた
- チェックイン同期が await だったため UI ブロックが起きており、fire-and-forget に変更した

## なぜ逸れたか
- response.ok 未チェックは「エラーが起きても処理が継続する」という設計ミス。
  safeFetch を作るまで個別に気づけなかった
- INVALID_TRANSITION のサイレント無視は「エラーを例外として扱わない」という意図的な設計だったが、
  状態が静かに壊れる問題が起きていた
- チェックイン await はリクエストの完了を待つ必要があると思い込んでいたが、UX 上不要だった

## 反省
- response.ok を全箇所で省いていたのは根本的な設計ミス。財務系 API（release-seat-auth）で見逃せば損失につながる
- INVALID_TRANSITION を握りつぶす設計は「失敗を隠す」実装。fail fast / ログ残しが正しかった
- fire-and-forget への変更でエラーを握りつぶすリスクが生まれた。後でログ監視を整備する必要がある

## 学んだこと
- safeFetch のような共通ヘルパーを最初から用意すれば response.ok 漏れは防げる
- reconcile バッチは「決済が途中で止まった場合の自動回復」として、複雑な決済フローには必須
- 状態遷移のエラーはサイレントに無視せず、少なくともログに残す。理想は fail fast

## 備忘

- reconcile バッチの実行頻度と Turso との差分検出ロジックが正しく動くか本番で確認する
