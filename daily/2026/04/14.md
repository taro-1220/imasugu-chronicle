## 横道に逸れたこと
- visitSession リファクタリング中にクーポン付与バグが発覚し、restaurant_id の修正が必要になった
- 決済 UI リデザインは visitSession とは独立したタスクだが、同日に大きく手を入れた
- Ops UI 追加は「デバッグのたびに DB を直接見ていた」問題への対処として割り込んだ

## なぜ逸れたか
- クーポン付与で restaurant_id がハードコード（モック値）のままになっていた。
  「どの店舗のクーポンか」が識別できず、クロス汚染の危険があった
- visitSession 移行は phase を分けて行ったが、Phase 2 完了で「来店中」の概念が正しく表現できるようになったため、
  Ops UI やクーポン UI など「来店中」を前提とした機能を同日に整備した

## 反省
- restaurant_id のハードコードは「テスト用の値を消し忘れた」典型ミス。
  環境変数や DB から取得する設計を最初から使うべきだった
- visitSession への移行は Phase を分けた設計は正しかったが、Phase 2 完了で一気に複数機能が動き出し、
  変更量が多くなった

## 学んだこと
- 「reservation を主語にする」設計では「来店中」というライフサイクルを表現できない。
  visitSession を主語にすることで来店開始〜終了を独立した概念として管理できる
- クーポンの restaurant_id は発行元を特定する重要キー。モック値を本番コードに残してはいけない
- Ops UI は運用上必須。デバッグのたびに DB を直接触る状態は持続不可能
