## なぜ逸れたこと
- P5-8 で public slots を API 経由に切り替えた際に、予約後の storeId 参照先が変わり null になっていた（未確認: 直接因果）
- Stripe Customer の SSOT 化が不完全だったため、同一ユーザーが異なるフローで複数 Customer を生成していた
- bill payment intent に冪等キーがなく、ネットワークリトライで重複が発生した

## 反省
- P5-8 のような API 切り替えは事前に storeId の参照経路を全て確認すべきだった
- Stripe Customer の one-to-one 制約は早期に enforce すべきで、SSOT 化の後回しが本番インシデントを招いた
- payment intent の冪等性は Stripe の基本原則なのに実装が遅れた

## 学んだこと
- API 切り替えは「切り替え前後でデータの引き継ぎ変数が変わらないか」を確認する
- Stripe は同一 customer に対して複数 PI/Customer が作られないよう upfront で guard する
- 本番インシデントが複数同時発生する場合、共通の変更（今日の API 切り替え）を疑う
