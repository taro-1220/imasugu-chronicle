- 領収書メールが送れていない問題を解消する

## 実際にやったこと
- 支払い完了直後に send-receipt API を直接呼び出す即時対応を実装
- 領収書メール送信を恒久対応構造（専用テーブル + 再送 API）に移行
- failed レコードの再送 API を追加
- webhook での email 取得に Stripe Customer fallback を追加
- bill_payment PI に customerEmail を確実に設定する修正
- bill_payment 前にメールアドレス入力を必須化
- 店舗データのアカウント分離バグ修正（複数アカウント混在）
- PublicSlot に ownerLoginId を追加してアカウント分離を強化
- 認証フロー最終修正（useAuthState hook + register page 3状態 UI）

## 横道に逸れたこと
- 領収書メール問題を追うと、webhook の非同期タイミング・email の null・
  Stripe Customer からの fallback・二重送信リスクと連鎖して修正が膨らんだ
- 認証フローの 3 状態 UI と店舗データ分離バグが、メール問題とは独立して同日に対処が必要になった

## なぜ逸れたか
- webhook が非同期で発火するため、クライアント側で決済完了を検知した時点では
  まだ webhook が処理されておらず、email が null のまま送信を試みていた
- Stripe の PI メタデータに email を持たせていなかったため、webhook だけでは取得できなかった
- 「支払い完了直後に直接呼ぶ」即時対応は webhook 依存を減らすが二重送信リスクがある
- 店舗データ混在は ownerLoginId で分離していなかった設計ミス。複数アカウントが同一キーを参照していた

## 反省
- 決済フローにおいてメールアドレスは「決済前」に確実に確保する設計にすべきだった。
  決済後に取得しようとすると非同期タイミングで必ず詰まる
- 二重送信リスクがある即時対応と恒久対応を同日に両方実装した。切り替えのタイミングが曖昧にならないようにする

## 学んだこと
- webhook での email 取得は「PI メタデータ → Stripe Customer」の順で fallback する
- 恒久的なメール送信管理は専用テーブル + 再送 API の構造が信頼性を担保する
- 店舗データは ownerLoginId 単位で分離しないと、複数アカウントのデータが混在する

## 備忘
