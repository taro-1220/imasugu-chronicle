## 最初にやろうとしてたこと
- 領収書メールの二重送信バグを解消し、ユーザー識別（canonical user_id）の設計を固める

## 実際にやったこと
- bill_payment webhook では領収書を送信しないように修正（seat_reservation のみ送信）
- メールアドレス取得位置を完了画面から決済画面に移動
- 登録モーダルを削除し、reservations テーブルに user_id カラムを追加
- email dedup・canonical user_id の確立
- email 正規化・canonical ID の同期引き渡し・dedup ログの安全装置を追加
- 店舗側予約一覧を DB 単一ソース（/api/business/reservations）に移行・masked email 表示
- クーポン自動付与を DB 経由に修正・運用補強
- 消費者 UI クリーンアップ（ヘッダー・トップ・左スライドパネルを削除）

## 横道に逸れたこと
- 二重送信修正を始めたら、webhook の種別（seat_reservation vs bill_payment）を
  区別していなかった設計ミスが判明し、webhook 側の分岐修正が必要になった
- canonical user_id の不在が判明し、email dedup・ID 同期・正規化の設計を一から作った
- 予約一覧が localStorage ベースだったため、DB 移行が別タスクとして発生した

## なぜ逸れたか
- bill_payment と seat_reservation の両 webhook で領収書を送っていた。
  「決済イベントが来たら送る」という雑な設計で、送信条件を webhook 種別で絞っていなかった
- canonical user_id がなかったのは「ユーザー識別」の設計を後回しにしていたため。
  同じメールアドレスでもデバイス・ブラウザが違うと別 user_id になる危険があった
- 店舗側の予約一覧は当初 localStorage で管理していた。DB 移行は事業者ダッシュボードの信頼性向上として必要になった

## 反省
- webhook の送信条件を「イベント種別」で明示的に絞る設計を最初から持つべきだった
- ユーザー識別（canonical user_id）は予約・クーポン・メール受信の根幹。後付けになったことで
  email dedup / ID 同期 / 正規化が連鎖する設計作業になった
- localStorage を SSOT として使う設計は、事業者側の信頼性要件に合わない

## 学んだこと
- webhook ではイベント種別（payment_intent.succeeded の metadata.type 等）で処理を分岐し、
  各種別ごとに副作用（メール送信等）を明示的に紐付ける
- canonical user_id は email を正規化（lowercase・trim）した上で dedup し、
  初回作成時の ID を canonical として以降は同期引き渡しする
- 事業者向け一覧は DB を SSOT にし、localStorage はキャッシュ層以外で使わない
