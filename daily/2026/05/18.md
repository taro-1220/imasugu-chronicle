## 横道に逸れたこと
- PI.customer / PM.customer の不一致修正（`f971c4e`, `f314595`）— sales 締めを実装中に Stripe 決済ログを確認してカスタマー ID の不一致を発見
- Stripe Elements の再マウント（`ee21c88`）— クーポン適用後に Elements が古い clientSecret のままになる問題に気づいた

## なぜ逸れたか
- sales 締め workflow の実装後に決済データを検証していると、PM と PI の customer が異なるケースが複数見つかった
- クーポン適用で clientSecret が変わるが、Elements がアンマウント/再マウントされないため古い UI のまま表示されていた

## 反省
- PI.customer / PM.customer の不一致は 05/07 から続く根本問題。根本修正ではなく「不一致なら使わない」という回避策になっている点に注意
- feature flag を `NEXT_PUBLIC_ENABLE_V2` で管理する設計は、server-side と client-side で値が異なるリスクがある（後日 05/20 で問題化）

## 学んだこと
- Stripe Elements は `clientSecret` が変わったら必ず再マウントする必要がある。同一コンポーネントが持ち続けると古いセッションの状態が残る
- 営業の open/close を明示的なフローにすることで、締め処理後の誤注文を防止できる
