## 横道に逸れたこと
- 会計 CTA 修正のつもりが、PM が customer に attach されていないという Stripe 側の不整合に当たり、attach → retrieve 検証 → PI.customer SSOT まで連鎖的に修正が必要になった
- 保存済みカードの修正をしているうちに、スナップショット復元のステータスチェック漏れが露見し、予約状態全体の調査へ広がった
- split payment の安定化試みが逆効果になりリバートが発生した

## なぜ逸れたか
- PM 修正の過程で「PI.customer と PM.customer が一致しない」という Stripe の制約に何度もぶつかった。根本は PM が customer に紐づかないまま決済が通ってしまうパスが複数存在していたため、1か所直すと別のパスから同じ問題が再現する構造だった
- スナップショット復元がステータスを無視していたため、キャンセル済み・支払い済みの予約が復元され「すでにキャンセル済みです」と即座に表示される問題があった。「UI が壊れた」と見えていたが、実態は状態復元の設計ミスだった
- split payment 変更は安定性確認が不十分だったためリバートに至った

## 反省
- dispatch() が同一ウィンドウで同期的に発火する性質を見落としていた。古い tracking effect の check() が stale な reservationId を持ったまま呼ばれ、新規予約直後に古い cancelled 予約が current にセットされていた。「登録直後にキャンセル表示」は UI バグではなく、クロージャが古い値を捕捉したことによる state の上書きだった
- ReservationsTab のレンダー本体で updateReservationStatus() を呼んでいた（副作用をレンダー中に実行するアンチパターン）。レンダーのたびに localStorage への書き込みが起き、dispatch() → ストレージイベント → 再レンダーの循環を引き起こしていた
- showActiveResNotice のダイアログが、handleSelectSlot で検出した conflict とは別の（より新しい）IM を参照していた。ダイアログを開いた時点のストレージをレンダー時に再引き当てていたため

## 学んだこと
- UI バグに見える問題の多くは state バグ。まず「誰が state を書いているか」「どのタイミングで書かれているか」を追う
- dispatch() は同期的にストレージイベントを発火する。effect のクロージャが古い値を持っている間に dispatch() を呼ぶと、古いコールバックが新しい state に介入する。canonical source を reservationId に絞り、effect 内では最新値だけを参照する設計にする
- PM を customer に attach するパスは複数存在し、それぞれが「attach されているはず」と仮定していた。SSOT を pm.customer に決め、取得→検証→保証のシーケンスを1か所に集約する必要があった
- スナップショット復元は「セッションコードが一致すれば復元する」だけでは不十分。status もチェックしないと、キャンセル済み・期限切れのスナップショットを復元してしまう
- ドキュメント（PAYMENTS.md / 不変条件定義）を書くタイミングは「バグを直した直後」が最も正確
