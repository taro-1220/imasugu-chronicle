## 横道に逸れたこと
- ownership gate を入れたことで、PI 作成前に reservation が存在しない既存導線が衝突し、決済順序の修正が必要になった
- split payment / item split は reservation・room・participant・PI の複数状態をまたぐため、gate 追加 1 つで戻る操作・キャンセル・stale PI 復元まで連鎖的に波及した

## なぜ逸れたか
- IDOR 対策を入れたことで、予約作成前に PaymentIntent を作る既存順序が ownership gate と衝突した
- 「未認証アクセスを塞ぐ」だけのつもりが、reservation を所有権の正本にするには決済前に reservation が必要だと分かった
- split payment は participant / room / PI / reservation の複数状態をまたぐため、1 つの gate 追加で戻る操作・キャンセル・stale PI 復元まで波及した

## 反省
- 決済導線を先に作り、ownership 境界を後付けしたため、PI 作成順序と reservation 作成順序が逆転していた
- c21a517 の fallback-open は一時的には通せるが、セキュリティ修正としては危険なので恒久化してはいけない
- split payment は「決済 UI」ではなく、reservation/session/room/participant/PI の状態同期問題として扱うべきだった

## 学んだこと
- セキュリティ修正は API に gate を足すだけでは終わらない。所有権の正本をどの時点で作るかが本体
- access_token を効かせるには、token を照合する対象である reservation が先に存在している必要がある
- IDOR 対策は状態遷移設計を逆算しないと、fallback-open や例外ルートが増えて逆に危険になる
- split payment は partial paid 後の戻る・キャンセル・stale PI の扱いまで含めてロック設計する必要がある

## 備忘
- c21a517 のような fallback-open は必ず後で除去確認する
- reservation before PI 作成が全導線で通っているか再監査する
- split payment / item split は ownership gate 適用後も stale PI・partial paid・cancel 不可条件を再検収する
- seat-hold / bill / split / item で access_token の渡し方が統一されているか確認する
- PAYMENTS.md の状態遷移定義と実装がズレていないか定期的に見る
