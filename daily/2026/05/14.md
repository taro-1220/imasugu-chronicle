## 横道に逸れたこと
- 二重支払い検出と自動返金（`c7ab5ab`）— Apple Pay キャンセルのリカバリ実装中に二重課金の可能性を発見
- 来店履歴の Supabase 取得（`af79d65`）— 割り勘の支払い確認で履歴を見ようとしたら localStorage から取得していた

## なぜ逸れたか
- 割り勘実装直後の動作確認で Apple Pay を使うと、キャンセル後に状態がおかしくなるエッジケースに気づいた
- 二重課金はリリース後に発生すると取り返しがつかないため即修正した
- 来店履歴が localStorage のみだと割り勘の別参加者に表示できないため Supabase 取得に切り替えた

## 反省
- 割り勘の MVP と同日にエッジケース（Apple Pay キャンセル・二重課金・record not found）を修正した。本来はフェーズを分けて実装 → QA → 修正とすべきだった
- 来店履歴の localStorage 依存は設計段階で気づけた問題。予約保持者以外に表示する要件が後から加わったため

## 学んだこと
- Stripe での Apple Pay は Web Payment Request API を経由するため、キャンセル後の PI 状態が通常の決済と異なる
- 二重課金防止は PI の冪等キーと状態チェックで対応。自動返金ロジックは「完了した PI が2件以上あれば後発を返金する」
